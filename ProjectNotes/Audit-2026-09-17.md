# Start-to-End Audit — every type of user (2026-09-17)

Ben asked: *"Can you run from start to end audit and find any errors, gaps or missing functionality
for every type of user?"* — then *"fix all of these and continue"*.

Six read-only sweeps ran in parallel over the whole tree: orphaned endpoints, unreachable pages,
write-only data, per-seat journeys, anonymous surfaces and privacy, and plan/capability gates.
`ProductWalk` ran as all seven seats on a fresh `IsHauntedDb_audit`. Every finding below that says
CONFIRMED was independently re-verified by hand before anything was changed.

**Baseline:** solution builds with 0 errors. Unit suite 6,368 passing, 2 skipped. Every new test in
the remediation was seen **failing against the unfixed code first**.

---

## The one-paragraph version

The audit's defining pattern is not bugs. It is **server capabilities with no entrance**: rules,
records and endpoints that were written carefully, documented well, tested where testable — and
that nothing ever called. Ten of the twelve fixes below are a route, a record or a column that
worked perfectly and had no button. The second pattern is **the browser knowing less than the
server**, so a control is offered and then refused on the click.

Both classes are invisible to unit tests by construction. That is why four of the fixes ship with
source-scan guards instead: no controller test can fail for having no caller.

## Severity 1 — live privacy exposure

### P1. A place published somebody's home address to anybody with the URL — CONFIRMED, fixed

`GET api/public/place/{id}` projected `StreetAddress1`, `ZipCode` and **exact** coordinates with no
`PlaceKind` branch and no approximation. It was the only anonymous surface in the tree that never
called `PublicCoordinates.Approximate`; every sibling does.

Traced end to end: `/places/{PlaceId:guid}` is signed-out, fetched with `GetAnonymousAsync`, plots
the map pin at the exact point for any kind, and falls the page **title** back to the street
address. `PlaceFactory` defaults `Kind = PrivateResidence`, so a client's home is the default shape
of a place row.

The projection dates from 2026-08-15 and predates both `PublicCoordinates` and the redaction work.
What made it *today's* exposure is that the public-place-hub arc turned `/places/{id}` into a
signed-out destination.

Worse than the sweep reported: the **`[Authorize]`** endpoint had the identical projection and no
scoping at all, so any free self-service account could read any residence's address by GUID.

**Fixed** — `PlaceDisclosure` is now the single definition. A residence publishes city, state and a
grid-snapped position; its name goes too, because a residence is routinely named after the family
living in it. The signed-in endpoint asks for standing (the caller's group worked there, they
created the row, or they administer the site) and otherwise serves the shape they would get by
signing out.

### P2. Two prose surfaces skipped the redaction rule — CONFIRMED, fixed

- **Link-preview card** returned a case title raw, so a published private-engagement case put the
  client's name in the card the case page itself would have substituted.
  `PublicProseRedactionTests` has a section per anonymous controller and had none for this one,
  which is exactly why nothing caught it.
- **`vote-summaries`** had no published-case gate, so the tally of a case since unpublished stayed
  readable. It answers a zero row now — the same answer an id with no votes gives, so it is not an
  existence oracle either.

### P3. An address marked Private still had its city published — CONFIRMED, fixed

`OrgPublicController` took the first address by Id with **no filter on either switch**. An owner
could mark an address Private, see a grey "Private" badge confirming it, and the group's public
page named that address's city and state anyway. `PublicDisplayMode.Hidden` was ignored the same
way.

## Severity 1 — destroys user work

### P4. A flagged contribution was held forever — CONFIRMED, fixed

Any signed-in reader can flag a published field session from the place page. That sets `Held`. The
public archive serves only `Approved`. The flag's own design note says **"the flag acts, then a
person decides"**, and accepts that it is abusable at this size for exactly that reason.

No person could decide. `GET`/`POST api/moderation/archive-media` had no caller anywhere — no
adapter method, no page, no nav entry — and the record they return lived in the API project, which
the website cannot reference, so the queue could not have been rendered even in principle. Every
assignment of `MediaReviewState = Approved` in the tree was traced: three in the publish path, plus
this orphaned endpoint.

Event evidence was the same shape and worse: its flag path wrote an `ArchiveReviewNote` documented
as being "for the moderator queue", and there was no queue endpoint at all.

**Fixed** — `/moderation/archive`, held rows shown by default, both kinds, the held reason
rendered. Guarded by `ModerationQueuesHaveAnEntranceTests` (route → adapter → page → nav).

  method at all; for experience types, the rename was called through a plain `PutAsync` that

## Severity 2 — a visitor could not find a place

CONFIRMED, fixed. The place hub is described as the public front door for a location and nothing let
a stranger reach one: no `/places` index, `/find` searches groups only, "Near me" returned groups
and events, and the nav has no Places entry. Item #88's stated shape asked for *"toggles for groups
/ events / places"* and the third was never built — the component documents its decision to drop the
**map** and says nothing about dropping places, which is what makes it an oversight.

Nearby search grows a places tier; two rules hold it honest — a private residence never appears, and
a place must have published work at it, because a place row is created by the first group to type an
address and listing them all would be a directory of typed-in addresses.

The reverse direction was missing too: a published case never linked its place. Public locations
only, so no public page points at a home.

## Deliberately NOT fixed — and why

### Ben's decisions, not mine to take

- **No custom role can hold any Events permission, on any plan.**
  `OrganizationPermissionArea.Events` was appended as area 10 *after* tiers were seeded, and
  `SubscriptionTierSeeder` deliberately skips any tier that already has area rows. Areas are
  inclusion rows that fail closed. So a group can build an "Event Staff" role, tick Event Bookings,
  assign it — and `HostedEventAccess` grants nothing. Owners and administrators pass by rank and
  would never notice. A venue lending its staff hits the same wall, so a non-member weekend helper
  works (event staff rows bypass the gate) and the venue's own night porter does not.
  **Already documented as awaiting your tick.** A seeder change would reach production, so it stays
  yours.
- **The $99 event credit is unreachable.** Nothing excludes `TierCapability.HostEvents` on any
  tier, and capabilities fail open, so `HostedEventEntitlement` never falls through to credits. Same
  reason: a pricing decision.

### Retired rather than wired — my judgment call, reversible

Three controls recorded a decision that nothing in the tree read. The surfaces their own labels
described do not exist (there is no address map on the public group page, no Directions button in
the address list, and the only member-facing address list is the manager's own screen, which must
show the full address to edit it). Wiring them meant inventing features; gating the one real map
would have broken address editing.

- "Enable map display for org addresses" (`ShowAddressMap`)
- "Enable directions for org addresses" (`ShowAddressDirections`)
- "Member display" on an address (`MemberDisplayMode`)

**Columns and API fields all stay**, so they return with no migration if you would rather the
surfaces were built. What is gone is the promise.

## Method notes worth keeping

- **A correction to my own note here.** I first recorded that the route guards silently miss ~8
  routes because those `.razor` files carry a UTF-8 BOM. That is wrong as stated, and a later sweep
  caught it. Measured: 15 `.razor` files under the website projects carry a BOM and 9 have `@page`
  on line 1 — but all four guards read through `File.ReadAllText`, which consumes the preamble, so
  `^` still sits against `@page` and all 9 match. Nothing is being missed today.
  What is true is narrower and still worth knowing: the regex is correct *by virtue of which API
  was used*. Switching any of those guards to `File.ReadAllBytes` + `Encoding.UTF8.GetString`, or a
  `StreamReader` with `detectEncodingFromByteOrderMarks: false`, would silently drop those 9 routes
  — `/login` and `/pricing` among them — and each guard's population floor (`> 10`) is loose enough
  not to notice. A shell `grep "^@page"` *does* miss them, which is where I got it.
- Nineteen hand-written copies of "published case" (`IsPublic && Status in (Public, Haunted)`) all
  agree today, including the two that were wrong on 2026-09-17. Nineteen copies at equilibrium is
  the state immediately before the twentieth edit; two comments in the tree ask for the named
  predicate that still does not exist.
- An EF `Include` on a **required** navigation is an inner join. A seeded row whose author has no
  `AppUser` silently vanishes from the result, which cost a diagnosis during this work.

# Round two — the crawl (same day)

Ben: *"then continue with the audit crawl"*. Six more read-only sweeps over dimensions the first
pass did not cover: silent failures, scheduled jobs, iOS contract drift, deletion completeness,
feature-switch coherence, and notification coverage. Then three more: authorization on the newest
surfaces, money correctness, and tests that cannot fail.

Round one's theme was **a capability with no entrance**. Round two's is **a promise the code does
not keep** — a doc comment, a help page or a UI label asserting something the code contradicts.
Almost every finding below was found by reading an intent and then checking it.

## The worst one is on the phone, and it shipped

Swift's `CaseStatus` declared four values whose numbers are not the server's. `MyCaseController`
returns `Ben.Data.Common.Enums.CaseStatus` outright — the same nine values `GroupCaseStatus`
already models correctly.

| server | client was shown |
|---|---|
| 2 Active | **Closed** |
| 3 Summarized | **Declined** |
| 4 Closed, 5–8 | — |

Not just a word: the detail view hid **Log what happened** while `status != .closed` was false, and
`.closed` was raw 2 — the server's *Active*. The one action a client has vanished on exactly the
cases being investigated and appeared on closed ones.

**What let it live:** the belief was written down. `GroupCaseRecords.swift` says *"that one is the
client's four-value view … the group's 2 is Active; the client's 2 is Closed."* A recorded false
belief is the most expensive kind, because it stops anybody rechecking. The old unit test asserted
`1 == .active` — the wrong mapping written down as a guarantee.

Fixed, with all nine asserted and the gate asking `isFinished`. Also from that sweep:
`MyCaseContact` read four field names the server has never sent, so "Who to contact" rendered names
with nothing to contact them by; and `MyCaseDetail.contacts` was non-optional against a nullable C#
parameter, where a null would have failed the whole screen — and `FixtureNullDriftTests` *asserted*
the key was required, which is the recorded claim that justified it.

## Scheduled jobs

All 18 jobs are registered and none is inert — the failures are in what they do.

- **Media retention deleted evidence it never warned about.** The class doc says the sweep "never
  deletes anything it has not already warned about"; the predicate said nothing of the kind.
  `WarnAsync` returns immediately with no relay configured and `SweepAsync` ran regardless, so on
  such a deployment nothing was warned and everything was deleted on schedule. Recordings live 7
  days, photographs 30 — somebody's only copy. Fixed with a notice requirement, a grace window, a
  late-notice path so nothing waits forever unwarned, and a log when retention is paused.
- **Billing notices repeated forever.** Markers were set inside the loop and saved once after it,
  while the mail committed independently — so one organisation throwing discarded the markers of
  everyone already written to, and they were written to again every five minutes. Worse, the throw
  escaped before `LapseExpiredAsync`, so **one broken group stopped every lapse on the platform**.
  Now per-item saves and per-section guards.
- **The mail scrub kept the letters that matter.** Both predicates required
  `AcceptedBySmtpUtc`, so a letter *given up on* kept its body and attachment bytes indefinitely —
  and the doc names the payload: "for a hosted event it carries the pass QR — a working door
  credential". Backwards: a letter that failed to a bad address is the one least worth keeping.
- **Stripe could charge twice across midnight UTC.** The idempotency key carried today's date, so
  a successful charge whose fulfilment failed stayed eligible and got a *new* key at midnight.
  Fixed by dropping the date: Stripe expires keys after 24 hours anyway, so a decline can still be
  retried tomorrow, and the date was duplicating that expiry while defeating dedup exactly where it
  was the only protection.
- **An anonymous submission about a stranger's home was kept for ever.** `PendingClientRequest`
  holds a street address, coordinates, gender, birth year and free text about somebody else's
  property; its own doc says rows are "ignored after `DateExpires`" and nothing swept them. New job.
- Two one-liners: a "say it once" warning that said it four times a day (an instance field on a
  scoped job — the reasoning was written two lines above and not applied), and a retention job
  documenting a research-page exception that no longer exists.

## Silent failures — 64 discarded mutations, and one root cause

**The transport never throws on a server refusal.** `DeleteAsync` returns `IsSuccessStatusCode`;
`PostAsync`/`PutAsync` return `default`. So a 403, 404, 400 or 402 — the exact things the server
guards emit — arrives as `false`/`null` and falls straight into the success path, and a
`try/catch` around a discarded write is **decorative**. It fires only on transport faults.

Eleven lose user content or make a false claim; all fixed:

- a client's typed occurrence, discarded with the dialog
- their decline and counter-proposal (Accept was guarded; these two were not)
- a withdrawn date proposal shown as withdrawn while the client could still accept it
- a green **"Saved."** on a 403 — and a refusal here is designed-for, not hypothetical
- four report-builder removals, on a report a client is about to read
- co-client access, invite revocation, related-person removal — "I removed their access" is a claim
  somebody acts on
- a file share the user believed reached a group
- cancelling an investigation, twelve lines above its own documented fix for the delete
- two "Reported" that may have reached nobody

Patterns 4 and 5 came back clean: every `(Result, Error)` tuple in the tree renders its sentence.
The violations are all of the other kind — paths that never asked for the sentence at all.

## Feature switches

Four closed the UI and not the door. The Messages tab opened onto FeatureGate's "Page not found"
*inside the tab strip* — the two tabs either side carry comments explaining why a gated tab must
not exist. Equipment kept working with Equipment off. Evidence voting and batch vote tallies
answered with Voting off. And `api/solo-plan` minted full organizations ignoring the
self-registration switch, against a doc comment about precisely that failure mode: *"a policy
control whose failure mode is believing you closed a door is worse than no control."*

## Notifications, and deletion

- **The primary client is never emailed about their own case.** `ClientStatusMailer` asks only
  `CaseClientAccess`, which exists only for *co-clients*; the client who asked reaches their case
  through `ClientRequest.AppUserId`. For the common shape — no co-clients — it logged "no client to
  mail" and wrote to nobody. `SubscriptionLapseJob` had this bug, fixed it, and wrote a paragraph
  about it. Every existing test seeds an access row, which is why it survived.
- **The group purge destroyed two records built to survive it.** An immutable file-deletion log
  with *no FK requiring it* — deleted only to satisfy a coverage guard that asks for the entity to
  be **named**, so it now takes a count instead — and the append-only billing ledger, now unlinked
  exactly as the outbox three lines above already was.
- **"Your photos are destroyed" was false.** Closure left the bytes "to the file sweeper". There is
  no file sweeper. That is the Apple 5.1.1(v) path, so the promise was relied on twice.

## A finding I passed on that was wrong

A sweep reported that leaving impersonation could strand a SuperAdmin *as* the impersonated user.
It cannot: the swap is local synchronous state and `IsImpersonating` is cleared unconditionally.
The real failure is narrower and already documented in the code — the `/api/me` round trip that
re-reads roles can fail, and you return **stripped of admin access** while the nav sends you to
`/admin/users`, which then refuses you. That is what was fixed. Worth recording because an agent
report is evidence, not a verdict.

## Method notes

- Six of these were found by reading a **doc comment, help page or entity summary** and checking
  it. That is the highest-yield technique in this codebase, because the intent is written down
  unusually well — which also means a stale sentence is load-bearing misinformation.
- `run-e2e.sh` uses `Verbosity=minimal`: passing tests print **nothing**, so a healthy run looks
  like ninety lines of "Skipped" and then half an hour of silence. Watch `api.log` in its
  `mktemp` dir instead. I killed a good run over this.

# Round three: the money

Ben: *"fix thge money finding too"*. Sixteen defects across billing, in two commits (`33873ea9`,
`62fe50ee`), plus four recorded for Ben rather than fixed. 41 tests, each seen failing against the
unfixed code before it was kept.

**The common shape.** Not one of these threw. Every one filed a wrong number and carried on, which
is why they were all still here in code that has been read several times. The audit technique that
worked was the same as round one's: read what a doc comment *claims*, then check whether the code
does it. Five of the sixteen were a sentence and its code disagreeing.

## Billing that stopped, or never stopped

1. **A SuperAdmin period edit stopped the card, silently.** `AdminOrganizationSubscriptionController`
   set `ProviderName = "Manual"` unconditionally; `StripeRenewalJob` selects `ProviderName ==
   "Stripe"`. Nudging a Stripe customer's end date by a day — the exact case the endpoint exists
   for — meant that card was never charged again. Every provider reference stayed in place, so
   nothing looked wrong on any screen; the group kept working until the period ended, then lapsed
   as if they had cancelled. **Worst finding of the round.**
2. **Nothing ever lapsed an overflow seat.** The renewal job matches Active seats past their period
   end, so a declined seat was retried *forever*; fulfilment dates the new period from the stale
   end, so six missed months became six charges in six days for one month of service. The
   organization path never had this because the lapse job removes it from `Status == Active` —
   seats were simply never added to that job.
3. **A seat's idempotency key carried the RUN date** after the organization path had dropped it.
   Stripe expires a key after 24 hours; a job retrying across midnight presents a fresh key for a
   period already paid for.
4. **Checkout never asked whether the group was already paid through.** A double click or a stale
   tab bought a month they owned — and the period was *overwritten* rather than extended, so the
   second payment bought nothing and left no trace of what it was for. Refused only for the same
   cadence, so a genuine monthly→yearly move still works.
5. **A member kept paying for a seat the group's own upgrade had covered** (`RenewSeatAsync` asked
   only "are they still a member"; its comment said "a seat has no band", which stops being true
   the moment the group re-bands). Both charges real, both recurring, neither billing page
   mentioning the other. Only the unambiguous case is decided — band covers *everybody* → every
   seat stops. A band covering some but not all seat-holders needs a rule about which survive;
   that is pricing, not a defect.

## A lapsed plan kept what it bought

6. **`TierAreaResolution` was status-blind**, against the rule `PaidPlan` states for the same
   question: *"Active, not merely present. A Lapsed subscription is not a paid plan — otherwise
   letting one expire would be a way to keep everything it bought, forever."* One paid month bought
   `PrivateResidenceCases`, `CaseTransfers`, `MediaMetadataStripping` and `HostEvents`
   indefinitely. Fixed in both the per-group gate and the listing, so the group finder cannot
   advertise what the gate refuses.

   **Checked before changing it** that no capability gates a *read*: `PrivateCaseGate`'s own
   remarks say it only bars new commitments, and `HostedEventEntitlement` is publish-time. So this
   costs a lapsed group nothing it already has, which is what item 84 promises.
7. **`SubscriptionLimitGuard` read its tier with no ordering at all** — arbitrary row, different
   answer per call, for any group with more than one subscription row.

   **Deliberately NOT given the lapse rule**, and this is the most important judgement of the
   round: these numbers include `PhotoRetentionDays` and `RecordingRetentionDays`, which
   `MediaRetentionPolicy` feeds to the job that **deletes**. Making a lapse shorten retention would
   erase a group's photographs for missing a payment, and item 84's promise is the opposite. A
   lapsed group is already stopped from *adding* by `RefusalIfLapsedAsync`, which is the whole of
   what lapsing is meant to cost. The reasoning is in the file because it looks like the same bug
   as (6) and is not.
8. **`AccountStorageGuard` held its own copy of `PaidPlan.CoversAsync`** — identical, so it was
   right, which is how drift starts.

## Arithmetic

9. **Tour proration rounded per unit then multiplied**: three tours cost $29.01 where three tours
   cost $29.00. Always *up* — the convention is away-from-zero — so the error never cancels and
   grows with the count.
10. **…and the ratio went through `double`** before being cast to `decimal`, next to a rounding
    boundary chosen precisely so half-cents go up.
11. **A fixed-amount coupon was spent again on every tour add-on.** It is already spent on the
    period's invoice, and nothing about an add-on decrements the redemption — so $50 off against
    tours prorating to $20 made every tour free, one at a time, for as long as the redemption
    lasted. Unbounded. Percentage coupons still apply, because a percentage is a statement about
    any amount; a fixed sum is a statement about one invoice.
12. **`CouponMath` asked "is this a percentage coupon?" two different ways** — `Misconfiguration`
    with `is > 0`, `PriceFor` with `is not null`. `PercentOff` 0 beside a real `AmountOff` took
    nothing off while reporting as applied; `PercentOff` −10 beside one billed **110% of list**,
    breaking `PeriodPrice`'s own stated contract ("Discount: never more than ListPrice. Payable:
    never negative").
13. **The admin ledger used banker's rounding** — `decimal.Round(x, 2)` with no mode, alone in a
    codebase that rounds money away from zero — **and taxed the unrounded figure while filing the
    rounded one**, so the row did not reconcile against itself. The ledger is append-only and
    receipts print from it.

## Documents that said the wrong thing

14. **Event-credit tax was charged frozen and filed live.** The checkout freezes the rate into the
    metadata *and* adds it to what Stripe collects; fulfilment discarded it and resolved again. Any
    change in between — a tax rule edited, the group's first address added — and the card statement
    says one number while the receipt says another.
15. **The tour add-on rewrote `PriceAtPeriodStart`**, the one field whose stated purpose is not to
    move. A $30 month with a tour added half way through read $44.50: neither what the period was
    sold for nor what the next costs. The add-on's money was already in the ledger with its own
    tax, reference and receipt number.
16. **…and priced the new tour from the live tier**, so a price rise reached a group mid-period.
    Now the contracted unit price unless the live one is cheaper — the rule
    `EffectiveTermsResolver` already states. **(15) is its prerequisite:** dividing a period price
    with add-ons baked into it would have invented a unit price nobody was ever quoted.
17. **The two-week notice told every non-yearly cadence "per month"** — a quarterly group read its
    quarterly price per month, understating the imminent charge by three, in the one letter whose
    purpose is that the charge is expected. It also quoted a tour business the price of **one**
    tour: $29 where the invoice is $87. That second bug already had a fix and a comment in the
    admin coupon path; it was never carried across.

## Left for Ben — each needs a decision, not an implementation

- **`Coupon.MaxRedemptions` can be exceeded concurrently by different groups.** The entity claimed
  its unique index made this safe; the index is on `(organization, coupon)`, so it holds the
  per-group limit and *cannot* express "at most N rows for this coupon". The false claim is
  corrected in place so nobody relies on it. The fix is a conditional increment in one statement —
  an `ExecuteUpdateAsync`, which the InMemory provider the fulfilment tests run on cannot execute.
  It should land with those tests moved to `SqliteTestDb`, not as an untested change to the
  payment path.
- **A receipt reprints the group's CURRENT name, billing contact and address**, although the
  controller says it is "generated from the frozen ledger row, so reprinting it in five years" is
  safe. The money is frozen; the party is not, so renaming or moving rewrites every past receipt.
  Needs two columns and a migration on financial records.
- **`OrganizationMergeService` deletes the merged group's `SubscriptionContractTerms`** while the
  sweep re-points its ledger rows to the base — the receipts survive and the contracts explaining
  them do not. Keeping them means a second subscription row per organization, which several call
  sites read with no ordering; that is a merge-semantics decision.
- **There is no refund, dispute or payment-failure lane at all.** Nothing in production code ever
  sets `EventCredit.RefundedUtc`. An unbuilt feature, not a defect.

## Corrected, not fixed

`OverflowSeats`' remarks claimed the band cap is frozen. The tier *identity* is frozen on the
subscription; its `MaxMembers` is read live, because no contract field records it —
`SubscriptionContractTerms` freezes the price, the tier name and the `SubscriptionLimit` caps, and
a band's member ceiling is none of those. Corrected to say what is true.

## Method note for next time

**Verify the blast radius before applying a rule uniformly.** (6) and (7) are the same-looking
defect; applying the same fix to both would have deleted paying customers' photographs. The check
that caught it was following `ValueOfAsync` to its consumers and finding a *deletion* job at the
end. Two minutes of tracing, and it was the difference between a fix and an incident.

## Correction: the money findings had not yet harmed anybody

I wrote into the deploy runbook that two of the billing defects were "actively costing money right
now". **That was false, and it was inferred from the code without looking at the data.**

A read-only pass over the live database (2026-09-17) found:

| | `IsHauntedDb` (live) | `IsHauntedDb_player` |
|---|---|---|
| Organizations | 1 | 12 |
| App users | 5 | 24 |
| Subscriptions | **0** | 2 |
| Member seats | **0** | 0 |
| Ledger rows | **0** | 0 |
| Coupon redemptions | **0** | 0 |

Nobody has ever subscribed. So every one of the sixteen defects is **preventive** — there is no row
to repair, no back-billing to decide, and no customer owed anything. The runbook is corrected and
now says to re-run the check before believing it on a later date, because it stops being true the
moment somebody subscribes.

**The lesson is the same one as the BOM claim in round one**: a defect in code is not yet a defect
in the world, and the step that tells them apart is querying the data. I asserted impact twice in
one audit without measuring it. Reading the code tells you what *would* happen; only the database
tells you what *did*.

The seven "0 rows" results from the first pass were also **vacuous rather than reassuring** — every
table they queried was empty, so a clean report meant nothing until the row counts were checked.
A zero from a query is worth nothing without its denominator.

### And the privacy finding had no live victim either

Same check, same answer. Round one's sharpest finding — `/places/{id}` serving a private
residence's street address, ZIP and exact pin to anyone with the URL — was recorded in the runbook
as "live on production now".

All six places on the live database are `PublicLocation`. **There is not one `PrivateResidence`
row.** The projection leaks nothing because there is nothing of that kind to leak.

The finding is still real and still worth deploying for, but the honest reason is the opposite of
urgency-about-a-breach: it should ship *before* the first person adds their own house, because that
person is the one exposed and would never know. Corrected in the runbook, with the one-line query
that re-checks it.

**Three impact claims, three overstatements, one audit.** The BOM, the billing, and this. In every
case the code reading was right and the claim about the world was wrong, and in every case one
query would have settled it. The rule to carry forward: *a finding describes code; an impact claim
describes data, and needs its own evidence.* Severity is not a property of a defect on its own — it
is a property of the defect meeting the rows that exist.

# Round four: auditing the DATA, not the code

The three corrections above all had the same cause — I read code and asserted things about the
world. So the next pass queried the live database instead, read-only, and it immediately found
something no amount of code reading would have.

## The finding: the live ladder gates NOTHING, and two components disagree about why

| | `IsHauntedDb` (live) | `IsHauntedDb_player` |
|---|---|---|
| Bands matching `FreeTierAsync`'s predicate | **0** | 1 ("Free") |
| Capability exclusion rows, anywhere | **0** | 2 |
| Bands granting the Events area (10) | 0 | 0 |
| Price rows selling an overflow seat | 0 | 0 |
| Organizations / subscriptions | 1 / **0** | 12 / 2 |

The live ladder is four paid bands — Small $20, Standard $40, Large $60, Enterprise $100 — and
**no band priced at nothing.**

`TierAreaResolution.EffectiveTierAsync` resolves a group with no subscription by calling
`FreeTierAsync`, which looks for an active, member-banded tier whose prices are *all* zero.
There is none, so it returns `(null, null)`, so `EffectiveTierAsync` returns null, so
`HasCapabilityAsync` returns `(true, null)` and `ResolveAsync` returns **ALL areas**. Fail open.

**So on the live site every group holds every capability**: `PrivateResidenceCases`,
`CaseTransfers`, `MediaMetadataStripping`, `HostEvents`. Item 184's whole paid lane — the
monetization premise — is unenforced. The one organization there, on no plan, paying nothing, may
take private-residence casework.

### Two components give opposite instructions

- `SubscriptionTierResolver.WhyGroupsCanStillBeFree` tells the administrator to **remove** a
  zero-priced band: *"A group is free by having no plan, not by being on a free one. Give the band
  a price, or take it out of the ladder."* The seeder's remarks say the same thing three times.
- `TierAreaResolution.FreeTierAsync` **requires** exactly such a band, or it gates nothing.

Production followed the first and therefore lands in the second's blind spot. Both cannot be right.

### Why it never failed a test

**The two databases differ in precisely the way that hides it.** The player copy still carries its
"Free" band and two exclusion rows, so every gate resolves and behaves. Nothing in the suite, and
nothing in a walk of the player copy, can see this.

### And my own F1 fix is inert against this configuration

Round three made `EffectiveTierAsync` require a *standing* subscription so a lapsed group stops
holding what it bought. On the live ladder a lapsed group falls through to `FreeTierAsync`, gets
null, and **fails open to everything anyway**. The fix is right and will work the moment a free
band exists; today it changes nothing on production. Said plainly because the commit message for it
reads as though lapsed groups are now gated, and on this data they are not.

Two other round-three fixes are inert for the same reason: no price row sets
`PricePerExtraMember`, so `OverflowSeats.MaybeOfferSeatAsync` always returns null and no seat is
ever offered — which makes the seat-lapse, seat-key and seat-double-billing fixes correct but
currently unreachable.

## The design gap underneath, and why I withdrew my own fix

My first instinct was a mirror advisory — "no band is priced at nothing, so nothing is gated" —
surfaced beside `WhyGroupsCanStillBeFree`. **I built it, it broke an existing test, and the test
was right.** Two things were wrong with it and both matter more than the warning:

1. **The two advisories are exhaustive.** A ladder either has a zero-priced band or it does not, so
   between them they flag *every* non-empty ladder. The admin screen would warn permanently, which
   is the same as not warning at all. `TierValidationShapeTests.A_healthy_ladder_says_nothing`
   asserts a healthy ladder is silent, and under my change no non-empty ladder could be.
2. **Its remedy created the other fault.** "Add a band priced at zero" is exactly what
   `WhyGroupsCanStillBeFree` tells you to undo.

That is not a bad warning; it is the sign of a real design gap:

> **There is no way to express "what a group with no plan gets" without also creating a band
> somebody can subscribe to for free.** A zero-priced band has to play two incompatible roles — a
> purchasable tier (where free is a fault, because holding a subscription reads as paid to every
> gate) and a *reference* tier defining the ungated baseline (where it is required). Nothing marks
> a band as reference-only.

**The one configuration that satisfies both predicates is an accident**, and worth knowing about
because it is load-bearing on the player copy:

| | filters on `Price.IsActive`? | predicate |
|---|---|---|
| `TierAreaResolution.FreeTierAsync` | **no** | `Prices.Any() && Prices.All(p => p.Price == 0m)` |
| `SubscriptionTierResolver.WhyGroupsCanStillBeFree` | **yes** | `Prices.Any(p => p.IsActive && p.Price <= 0m)` |

So a free band whose zero prices are all `IsActive = false` is found by the resolver (gating works)
and ignored by the advisory (no complaint) — because one method filters on `IsActive` and the other
forgot to. That is the only sound state available today and nobody chose it deliberately.

**Nothing was changed.** The code is reverted and the suite is back to green. Whether an
unsubscribed group should be gated, by what, and how a reference band is expressed, are Ben's
decisions — and flipping fail-open to fail-closed on a live site is how real people get locked out
of something that never said it would. Recorded rather than guessed at.

## Method note: a zero is worth nothing without its denominator

The first production pass returned seven clean results. All seven were **vacuous** — every table
they queried was empty. "No problems found" and "nothing to find problems in" look identical in a
row count, and only the scale query told them apart. Always ask for the denominator in the same
breath as the finding.
