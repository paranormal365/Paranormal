## 3. Item 239b — enqueue a letter inside the caller's transaction

**The gap.** 239a made every letter an outbox row, but `OutboxEmailService.SendAsync` opens its
own `DbContext`. A booking that commits and a confirmation that fails to enqueue (or the reverse)
leave a hairline window: a guest confirmed with no letter, or a letter for a booking that rolled
back.

**The plan.**
1. ~~Add an overload: `EnqueueAsync(BenDataContext callersDb, EmailMessage message)`~~ **DONE
   2026-09-22.** On `IOutboxEmailQueue` rather than `IEmailService`, because that interface lives in
   `Ben.Data.Common`, which cannot see `BenDataContext`. Registered as the SAME singleton instance
   behind both interfaces. It throws where `SendAsync` swallows, deliberately: the contract is
   "both or neither", so a letter that cannot be queued must stop the caller's write. Four SQLite
   tests, and the rollback one is proved discriminating — pointed at `SendAsync` it fails, because
   that method has already committed a row of its own.
2. ~~Convert the callers~~ **DONE 2026-09-23 — the transaction approach, Ben's choice.** Both
   `SendAskedAsync` callers now open a transaction around save → enqueue → save and commit once;
   `EventGuestMailer.SendAskedAsync` queues through `IOutboxEmailQueue` and throws if it has none,
   rather than falling back to the non-atomic path. Three things found on the way:
   - **The attendance controller opened the transaction unconditionally**, which put the plain
     event's tour welcome — sent through `IEmailService`, so on a connection of its own — inside a
     transaction for no reason. Now opened only when there is a hosted request (`asked`). The two
     never meet today, since a hosted event always asks rather than comes.
   - **`EnqueueAsync` read the opt-out through a context of its own**, i.e. a second connection
     inside the caller's transaction. That query joins `AppUsers`, which a booking writes, so where
     readers wait on writers it stalls to the command timeout and the lookup's catch then sends the
     letter anyway. It now reads through the caller's context. **Not live:** `BookingAsked` cannot
     be declined, so the check returns before opening anything; and read-committed snapshot is ON
     for both `IsHauntedDb` and `IsHauntedDb_player` (checked 2026-09-23) — but nothing in the
     repository turns it on, so a rebuilt database would not have it.
   - The template lookup (`MailComposer`) still reads on its own connection inside the
     transaction. Left alone deliberately: it reads only `EmailTemplates`, which no caller writes,
     and its misses are cached.
   **Tests:** `ABookingRequestCommitsWithItsLetterTests` — a request commits with exactly one
   `booking-asked` letter, and a queue that throws after the first save leaves no request; the
   second was run against the controller with its transaction removed and fails.
   `ALetterCommitsWithWhatItIsAboutTests` gains a count that queueing opens no context of its own;
   run against the old side read, it fails. (Its first draft asserted only that the opt-out held
   and passed against the broken code — SQLite shares one connection, so the "second" read just
   works. Recorded because it is the trap.) Full `Ben.Web.Tests`: 6796 passed, 0 failed.

   *Original note, 2026-09-22:* **this is not the mechanical step it looks like.**
   Both callers of `SendAskedAsync` (`PublicHostedEventBookingController:664`,
   `PublicEventAttendanceController:410`) **save first and mail second**, and the mailer re-queries
   the booking by id through `LoadAsync`. So enqueueing before the save finds no row, and
   enqueueing after it without a second save adds the letter to a context nobody saves again —
   losing it silently, which is worse than the window being closed. Each caller needs either an
   explicit transaction around save/enqueue/save, or the mailers reshaped to take the entity
   already in memory instead of an id. A decision about which, before any of them move.
   Identity's own mail (`IEmailSender`) cannot take a context and stays where it is.
3. `EveryMailerGoesThroughTheOutboxTests` already exists; add a guard that a caller holding a
   `DbContext` and calling the context-less overload is named — the same ratchet shape as the
   sender list.

**Test:** ~~on SQLite, a save that throws after `EnqueueAsync` leaves no outbox row; a save that
commits leaves exactly one.~~ Done in step 2, at the controller rather than only the queue.

**The decision letter — DONE 2026-09-23.** `SendDecisionAsync` (confirmed / turned down /
released, and the letter the pass travels in) now queues into the caller's context and does not
save. Four callers:
- **Confirm and turn-down/release** go through a new `BenControllerBase.SaveInOneTransactionAndAuditAsync`:
  save the decision, queue the letter and stamp the pass, save, commit — then audit. The audit
  moved AFTER the commit because `IAuditLogService` writes on its own connection: inside the
  transaction it would commit alone, and a rollback would leave a record of a decision that never
  happened.
- **Both "send the pass again" endpoints** (host's and guest's) save the letter and the pass's
  `EmailedUtc` in one save, and turn a failure into their existing refusal, logged at Error.
  **That fixed a live bug:** the send swallowed its own failures, so the pass was stamped as
  emailed and the host told 200 for a letter that did not exist — the exact thing that endpoint's
  own doc comment forbade.

**A rule changed on purpose.** The mailer used to catch everything on "nothing here may undo a
decision the venue has made" — right while the letter was a call to a mail system. It is now a row
in the same database, sent later by the outbox and retried there, so failing to write it means the
database failed; the host is told to try again rather than left believing a guest has their pass.
The old test holding that rule (`A_send_that_throws_never_undoes_the_decision`) was rewritten to the
new one, not patched.

**Tests:** `ABookingDecisionCommitsWithItsLetterTests` — a confirmation commits with its pass and
one `booking-decided` letter; a queue that throws leaves the booking Requested with no pass; a
resend that cannot queue answers Conflict and stamps nothing. All three fail against the committed
pre-change code, and removing only the transaction fails exactly the rollback one.
`ForwardingOutboxQueue` hands queued letters to a test's `IEmailService` fake, so the tests about
what a letter SAYS keep working — and is documented as proving nothing about atomicity.
Full `Ben.Web.Tests`: 6799 passed, 0 failed.

**The invitation letters — DONE 2026-09-23.** Five letters, each carrying a link to a token, and
four of them ROTATE that token when somebody is invited again — killing the link in the letter
they already have. Every one saved the token first and wrote the letter after, through an outbox
that swallows its own failures.

| Letter | Where | Now |
|---|---|---|
| "…invited you to a case" | `MyCaseController.InviteCoClient` | queued before the ONE save |
| "Confirm you're coming" | `PublicEventAttendanceController.RequestAttendance` | queued before the ONE save |
| "You're signed up for" | `OrgCalendarEventController.InviteGuest` | queued before the ONE save |
| "You're invited to" (venue) | `HostedEventBookingController.InviteByEmail` | queued before the ONE save |
| "Can you help at…?" (staff) | `EventGuestMailer.SendStaffInviteAsync`, both staff actions | save, queue, save — one transaction |

The first four build their letter from values already in memory, so one ordinary save carries the
token and the letter: atomic without a transaction. The staff letter reads its row back by id, so

Out of scope and handed off as its own task: three of these log the live link when mail is not

`AccountMadeForYou` stays where it is: it goes through Identity's `IEmailSender`, which cannot take

**Tests:** `AnInvitationCommitsWithItsLetterTests`, one per letter, with the outbox wired as
