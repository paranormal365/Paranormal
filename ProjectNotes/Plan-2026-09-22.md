## 1. Item 244 — the dashboard: swap the chart library, and only then think about a rollup

**Where it stands.** Measured twice. The server is not the cost (every endpoint under 120 ms
cold, ~1 ms warm); **~85% of page load is drawing charts in the browser**, because ApexCharts is
SVG and a DOM node per point: 397 ms at 365 points, 1,329 ms at 730. Chart.js on canvas is flat
(6–7 ms at any count). The eight-chart mix: **ApexCharts 334 ms, Chart.js 33 ms**, and 201 KB
against 563 KB. Ben's "five seconds" was never reproduced; he chose to watch it.

**The plan.**
1. `ApexChart.razor` is the one wrapper; give it a Chart.js twin with the same parameters
   (`Series`, `Categories`, `Kind`, theme colours from the site's tokens) so callers change one
   tag name, not their data.
2. Convert the dashboard's eight charts; keep the legend theme-aware (V4 showed the current one is).
3. The activity chart's 365-point series is the proof: measure before/after in the browser with
   the same harness that produced the table above, and write the numbers into the item.
4. Leave ApexCharts in place for any chart not converted; remove the package only when nothing
   references it.
5. **The rollup stays deferred** until a measurement on real data says a count is the cost. The
   pieces (`IScheduledJob`, `ScheduledWorkService`, `ScheduledJobLedger`) exist; the trigger is
   a number, not a feeling.

**Tests:** the dashboard renders every chart with no console error as SuperAdmin (the sweep
already checks this), plus a unit test that the twin wrapper maps the same inputs.

## 3. Item 239b — enqueue a letter inside the caller's transaction

**The gap.** 239a made every letter an outbox row, but `OutboxEmailService.SendAsync` opens its
own `DbContext`. A booking that commits and a confirmation that fails to enqueue (or the reverse)
leave a hairline window: a guest confirmed with no letter, or a letter for a booking that rolled
back.

**The plan.**
1. Add an overload: `EnqueueAsync(BenDataContext callersDb, EmailMessage message)` that adds the
   `OutboxEmail` row to the caller's context and does **not** save — the caller's `SaveChangesAsync`
   commits both or neither.
2. Convert the callers that own a transaction and send a letter about what they just wrote:
   booking confirmation and decision, tour sign-up approval, guest-code issue if it ever mails,
   the account-handover letter. Identity's own mail (`IEmailSender`) cannot take a context and
   stays on the existing path — say so in the interface remarks.
3. `EveryMailerGoesThroughTheOutboxTests` already exists; add a guard that a caller holding a
   `DbContext` and calling the context-less overload is named — the same ratchet shape as the
   sender list.

**Test:** on SQLite, a save that throws after `EnqueueAsync` leaves no outbox row; a save that
commits leaves exactly one.
