## Database Script (`scripts/create-database.sql`)

A complete idempotent SQL Server schema script was generated from all EF Core migrations.

### How to regenerate (run after every new migration)

```bash
cd /path/to/Ben
dotnet ef migrations script \
  --project Ben.Data.Source \
  --startup-project Ben.Data.WebApi \
  --output scripts/create-database.sql \
  --idempotent
```

`--idempotent` wraps every migration block in an existence check — safe to re-run against an existing database and only applies missing changes.

### How to apply to a running SQL Server

```bash
# Docker dev instance
sqlcmd -S localhost,1433 -U sa -P YourStrong@Password1 \
       -d BenDb -i scripts/create-database.sql

# Or in SSMS / Azure Data Studio: open the file and execute
```

## Development → Production Deployment Guide

### Option A — EF Core migrations (recommended; no raw SQL required)

The cleanest path for a new environment: let EF Core apply migrations directly against the target database.

```bash
# 1. Set the production connection string
#    (appsettings.Production.json or environment variable)
export ConnectionStrings__DefaultConnection="Server=prod-sql;Database=BenDb;..."

# 2. Apply all pending migrations
dotnet ef database update \
  --project Ben.Data.Source \
  --startup-project Ben.Data.WebApi

# 3. Run the WebApi — seeders run automatically at first startup:
#    SuperAdminSeeder  → creates SuperAdmin role + user
#    OrganizationSeeder → seeds BenCo org + members (if SeedData:SeedOrganization:Enabled=true)
#    UploadFileTypeSeeder → creates "Logo" file type + image extensions
dotnet run --project Ben.Data.WebApi/Ben.Data.WebApi.csproj \
           --environment Production
```

### Option B — SQL script (`scripts/create-database.sql`)

Use when EF tooling is not available on the deployment target (e.g., CI/CD pipeline, DBA-managed server).

```bash
# 1. Create an empty database named BenDb (SSMS, sqlcmd, or Azure portal)

# 2. Execute the script
sqlcmd -S <server> -U <user> -P <password> \
       -d BenDb -i scripts/create-database.sql
```

The script is idempotent — re-running it on a partially initialised database only applies the missing migrations.

### Option C — Docker (dev/staging)

```bash
# Start the same SQL Server container used in development
docker run -e ACCEPT_EULA=Y \
           -e MSSQL_SA_PASSWORD=YourStrong@Password1 \
           -p 1433:1433 --name bendb-sql \
           -d mcr.microsoft.com/mssql/server:2022-latest

# Apply migrations (Option A) or execute the SQL script (Option B)
```

### Connection string format

```json
// appsettings.Production.json (or environment variable)
{
  "ConnectionStrings": {
    "DefaultConnection": "Server=<host>,<port>;Database=BenDb;User Id=<user>;Password=<pass>;TrustServerCertificate=True"
  }
}
```

## Late-Session Work (Entra fix + User Detail CRUD + WaveSurfer)

### 14 — SuperAdmin DB-Based Authorization (`SuperAdminHandler`)

Root cause of all admin page failures: `[Authorize(Roles = "SuperAdmin")]` uses the default JWT scheme's role claims. With Entra v2 tokens, `IClaimsTransformation` was correctly running but the enriched claims weren't being used by the `RolesAuthorizationRequirement` check.

**Fix:** Created `Ben.Data.WebApi/Authorization/SuperAdminRequirement.cs` + `SuperAdminHandler` — a custom `IAuthorizationHandler` that checks roles **directly from the DB** via `UserManager.IsInRoleAsync`. Three paths:

1. Local Identity bearer → `User.IsInRole("SuperAdmin")` (role claim, fast path)
2. Entra token with `app_user_id` claim → `FindByIdAsync` → `IsInRoleAsync`
3. Entra token OID fallback → `FindByLoginAsync("Microsoft", oid)` → `IsInRoleAsync`

Changed all 5 admin controller classes from `[Authorize(Roles = RoleNames.SuperAdmin)]` to `[Authorize(Policy = RoleNames.SuperAdmin)]`. Registered the named policy + handler in Program.cs.

**Result:** Roles grid ✅ · View user detail ✅ · All admin endpoints working for Entra users.
