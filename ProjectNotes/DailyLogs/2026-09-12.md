## 1. iOS 1.0.2 build 4 — REJECTED under Guideline 2.1(a), fixed as build 5

> *"We were unable to access the app because the app came back to login page when we logged in with
> Apple."* — iPhone 17 Pro Max, iOS 26.6.2.

**Not metadata. A real bug, and it made Sign in with Apple impossible for every Apple identity with
no account here.**

An unknown identity cannot become an account without a display name and a permanent @name, so the
server answers `409` and the app should open the "Almost there" form. It never opened. The sheet
hung off the `Section` that draws the Apple button, and that section's own rows change in the very
instant the sheet is asked for — the in-flight spinner is removed by `defer { busy = false }`
immediately after `collecting = true`. SwiftUI answers by tearing the presentation down **and
dismissing the sign-in sheet that contains it**.

**Reproduced twice before changing anything**, on an iPhone 17 Pro Max simulator (iOS 26.5):

1. A standalone SwiftUI probe with the same shape dismissed the outer sheet and presented nothing.
   The same probe with the sheet hoisted to the form worked. So did a variant with no row churn —
   which is why it survived a code read and a casual test.
2. The shipped `AppleSignInSection`, driven through the 409 branch by a temporary button, returned
   to the signed-out Profile. With the fix and the same button, "Almost there" opens with Apple's
   name prefilled.

**The fix.** `AppleSignInFlow`, an `@Observable` object owned by `SignInView`, which presents the
form from its own navigation stack. Plus a second silent path closed: the old code dismissed the
sign-in form whatever `api/me` answered, so a session that died between the token and the identity
produced the identical symptom. Dismissal now waits for `SessionStore` to reach `signedIn`.

**Also learned:** only `collecting = true` can make that sheet vanish, so the reviewer's token
**did** validate against production. `Apple:ClientIds` and the whole server side were fine.

`CURRENT_PROJECT_VERSION` 4 → 5, archived to the Organizer, signed with Apple Development because
the distribution certificate is not on this Mac — Organizer re-signs at Distribute. Left for Ben.

## 2. Field Kit — the camera, and what one upload carries

**The camera was always there and nobody could find it.** Photographs always, video clips behind
the video channel, and the camera itself as a Sentry motion sensor. But a session started with
field, sound and location, video was off, and the video button only appears once the channel is on —
so the only place to turn it on was a panel down a running session's screen, at the hour of night
when nobody hunts for settings.

- **Channel picker on the New session sheet**, each channel with its battery cost. Channels persist
  on the session row (`channelsRaw`, optional so SwiftData migrates it without being asked), so a
  relaunch comes back recording the same things.
- **Ben's rule, after a first pass got it wrong: the phone is never limited, the upload is.** Record
  all night at whatever the camera gives. One upload carries **5 minutes of video and 500 MB**;
  readings, marks, photos and sound are not rationed by time, because a minute of video outweighs
  an hour of everything else.
- **Too long and too heavy get different answers.** Length needs clips, so the screen says how much
  to drag off. Weight offers a down-convert — 1080p or 720p, 24 fps — with the projected size beside
  each choice, via `SessionVideoConverter` writing into the upload's scratch directory.
- **Groundwork only, and marked as such:** `VideoRecordingMode` (clips by hand / continuous clip-later
  / continuous clip-live, each with a battery note, default the cheap one) and `ClipPlanner` (8 s
  lead-in, nearby triggers merged, 90 s cap). The capture pipeline is NOT built:
  `README-continuous-video-and-auto-clips.md` says so and says why none of it can be verified in a
  simulator.

20 BenKit tests for the allowances, 13 for the clip planner, 3 UI tests for the picker.

## 5. Item 235 phase 2 — bookings

### 2.1 — the model (`46e5a42c`)

Six tables, four columns, all additive. Migration `HostedEventBookings`, `Up` reviewed operation by
operation (4 AddColumn, 6 CreateTable, 18 CreateIndex, no drops), applied to `IsHauntedDb_player`.

- **A booking is a party, not a person.** Four people arriving together are one row with one lead and
  named guests. Four sign-ups would ask the host which four share a room, and would let three cancel
  while the fourth kept a room built for four.
- **Nights are rows, not a range**, because capacity is asked per room per night.
- **A guest needs no account.** Somebody brings a partner who will never hear of this site.
- **`HostedEventBookingStatus` is new, not `TourSeatStatus` reused.** That one cannot say a guest
  withdrew, because a walk's sign-up is simply deleted and a booking cannot be: the room-nights and
  the dietary notes the kitchen catered against are a record. And a room is *confirmed*, not
  *reserved*.
- **`EventCapacity`** mirrors `TourSeats`: only `Confirmed` holds anything, party size 0 still counts
  as one person, a null capacity cannot be over-filled while zero sleeps nobody, and editing excludes
  the booking's own beds. 27 tests, proved to discriminate (a request holding a bed failed 3;
  counting the event instead of the night failed 1).

### 2.2a — the venue's side (`092827e8`)

The board is one call: rooms offered, occupancy per room per night, every booking. Confirm can put a
party somewhere other than what they asked for. Every refusal names the room, the date and how many
more it sleeps.

Confirmation writes the umbrella attendee with `Accepted` + `Reserved` and `Seats` = party size — the
pair every existing count already understands — and a test asserts `TourSeats.PlacesTaken` reads it.

**A guard caught a real defect.** `OrganizationPurgeCoverageTests` named
`HostedEventBookingNights.PlaceRoomId` and `HostedEventRooms.PlaceRoomId` as NoAction references the
group purge never deletes, so deleting a group would have been refused by the database — the exact
failure that hit production twice before that guard existed. Both now purged before `PlaceRooms`.

### 2.2b — the guest's side (this commit)

`PublicHostedEventBookingController`: ask, read, change, acknowledge, withdraw, and `mine`.

- **Asking holds nothing and is not capacity-checked.** Refusing a request because a room is full
  would close the waiting list the host wants.
- **Withdrawing means two different things.** A request is simply deleted — nobody was holding
  anything. A **confirmed** booking is not: the venue has catered, staffed and possibly turned
  somebody else away against it, so the guest ASKS and the host releases it. A room freed without
  the host knowing is a room that stays empty. New columns `CancellationRequestedUtc` and
  `CancellationReason`, migration `HostedEventBookingCancellationRequests`.
- **A guest editing what the venue agreed to sends it back as a request**, because the thing the
  venue said yes to is not the thing being asked for any more. A party that quietly grew from two to
  six would be sleeping in a room nobody checked.
- **One booking per person per event means one LIVE booking**, or somebody who cancelled in March
  could never come in October.
- The guest's record is deliberately not the host's: no other party's details, no decision-maker's
  name, no dietary note but their own party's.

13 behaviour tests on `SqliteTestDb` with foreign keys on, proved to discriminate by dropping the
unique index and watching the two-rooms-on-one-night test fail.
