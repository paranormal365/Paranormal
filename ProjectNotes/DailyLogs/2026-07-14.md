### Bug Fix — Administration Button Never Appearing / Login State Lost on Reload

These two issues share a common root cause and were fixed together.

#### Root Cause A — Opaque tokens from Identity API

`AddIdentityApiEndpoints` / `MapIdentityApi` issues **data-protected opaque tokens**, not JWTs. `JwtClaimsParser.ParseClaims` splits on `.` and expects a 3-part JWT; a data-protected token is a single base64url blob, so the parser always returned `(null, false)`.

Consequence: `IsSuperAdmin` was always `false` → the Administration button (which guards on `TokenStore.IsSuperAdmin`) never rendered.

**Fix — `GET /api/me` endpoint (`Ben.Data.WebApi/Controllers/MeController.cs`):**
```
GET /api/me  →  { UserId, Email, IsSuperAdmin }
```
Uses `UserManager<AppUser>.IsInRoleAsync(user, "SuperAdmin")` server-side, where role information IS available.

**Fix — `WebApiAuthService.LoginAsync`:**
After storing the token (which sets `AccessToken` and makes the bearer handler work), calls `GET /api/me` to correctly set `IsSuperAdmin` and `UserId`.

#### Root Cause B — In-memory token store lost on page reload

`WebApiTokenStore` is a Scoped DI service. Page reload = new Blazor Server circuit = new `WebApiTokenStore` instance = all tokens gone.

**Fix — `IWebApiTokenStore` + `WebApiTokenStore`:**
Added `event Action? StateChanged` and `NotifyStateChanged()`. Called at the end of:
- `LoginAsync` (after `/api/me` returns)
- `Logout`
- `ImpersonateAsync`
- `StopImpersonating`
- `WebApiBearerTokenHandler.RefreshIfNeededAsync` (after refresh)

**Fix — `MainLayout.razor`:**

Subscribes to `TokenStore.StateChanged`:
```
StateChanged → PersistAuthStateAsync() → ProtectedLocalStorage["ben-auth-state"]
            → StateHasChanged()  (re-renders AppBar with correct IsSuperAdmin)
```

`OnAfterRenderAsync(firstRender)` restores auth state from `ProtectedLocalStorage` before making the user-count API call. `ProtectedLocalStorage` is encrypted by ASP.NET Core Data Protection.

Persisted fields: `AccessToken`, `RefreshToken`, `ExpiresAtMs`, `UserEmail`, `UserId`, `IsSuperAdmin`.  
Impersonation state is intentionally **not** persisted (transient session concept).

**Unsubscribed in `Dispose`** to prevent memory leaks.

### Refactor — `OrganizationUserMembership.Role` (replaces `IsOrganizationAdmin`)

#### Motivation

`IsOrganizationAdmin` (bool) was a coarse two-state flag. The security model already had a five-level `OrganizationMemberRole` enum in `Ben.Service.Security.Models`; this change wires it through the full stack.

#### `OrganizationMemberRole` enum placement

`Ben.Service.Security` references `Ben.Data.Source` (entity layer). `Ben.Data.Source` cannot reference `Ben.Service.Security` in return — circular dependency. Because the entity property type must resolve at the data layer, the enum is defined in **`Ben.Data.Common.Enums`** (where both layers can reach it). `Ben.Service.Security` imports it via a using alias to preserve the intent of keeping security concepts in the security project:

```csharp
// Ben.Service.Security/Services/OrganizationSecurityService.cs etc.
using OrganizationMemberRole = Ben.Data.Common.Enums.OrganizationMemberRole;
```

#### Enum values

| Value | Int |
|---|---|
| `Owner` | 1 |
| `Administrator` | 2 |
| `Manager` | 3 |
| `Member` | 4 |
| `Viewer` | 5 |

#### Access control semantics

`Owner` and `Administrator` have full org access (replacing the old `IsOrganizationAdmin = true` check). `Manager`, `Member`, and `Viewer` require explicit `OrganizationAccessGrant` rows for specific table/action permissions.

#### Migration — `ReplaceIsOrganizationAdminWithRole`

Three-step `Up()` to preserve existing data:
1. Add `Role int NOT NULL DEFAULT 4` (Member)
2. `UPDATE OrganizationUserMemberships SET Role = CASE WHEN IsOrganizationAdmin = 1 THEN 1 ELSE 4 END`
3. Drop `IsOrganizationAdmin`

Applied to `bendb-sql`. DB now has 8 migrations all Applied.

## Session 4 — Entra Login End-to-End Debugging (Browser Test)

### Overview

Successfully completed the Entra login flow end-to-end. Three separate bugs found and fixed. 209/209 tests still passing.

---

### Bug 1 — "Correlation failed" on Microsoft callback

**Symptom:** `AuthenticationFailureException: Correlation failed` when Microsoft redirected back to the app.

**Root cause:** OIDC `CorrelationCookie` and `NonceCookie` default to `SameSite=None; Secure`. The app runs on plain `http://localhost:5078`, so the browser refuses to transmit `Secure` cookies back on the callback.

**Fix** (`Ben.Web.WebApp/Program.cs`, inside `AddOpenIdConnect`):
```csharp
oidc.CorrelationCookie.SameSite = SameSiteMode.Unspecified;
oidc.CorrelationCookie.SecurePolicy = CookieSecurePolicy.SameAsRequest;
oidc.NonceCookie.SameSite = SameSiteMode.Unspecified;
oidc.NonceCookie.SecurePolicy = CookieSecurePolicy.SameAsRequest;
```
`CookieSecurePolicy.SameAsRequest` means non-secure on HTTP, secure on HTTPS — safe for both dev and production.

---

### Bug 2 — Returned to site but not logged in (middleware + WebApi config)

**Symptom:** After correlation error was fixed, Microsoft returned to the app but the user was not logged in (still showed Sign In button).

**Root causes (two issues):**

**a) Middleware claim filter was wrong**

The Entra token capture middleware checked:
```csharp
user.HasClaim(c => c.Type == "iss" || c.Issuer.Contains("login.microsoftonline.com"))
```
`c.Issuer` is the local scheme name (e.g. "Cookies"), not Microsoft's URL. `iss` is not mapped into cookie principal claims by default. The check always returned `false`, so `EntraTokenHolder` was never populated.

**Fix:** Simplified to:
```csharp
if (user.Identity?.IsAuthenticated == true)
```
Safe because in the WebApp, HTTP-level authentication only ever comes from the OIDC cookie.

**b) WebApi had no AzureAd config**

`Ben.Data.WebApi/appsettings.Development.json` had no `AzureAd` section, so `entraEnabled = false` in the WebApi. All Entra JWTs sent to `/api/me` were rejected with 401.

**Fix** — added to `Ben.Data.WebApi/appsettings.Development.json`:
```json
"AzureAd": {
    "TenantId": "common",
    "ClientId": "e75f71ef-cc2e-43ad-ba0f-9e24c6f805f1",
    "Audience": "api://e75f71ef-cc2e-43ad-ba0f-9e24c6f805f1"
}
```

---

### Bug 3 — Still not logged in (Blazor DI scope isolation)

**Symptom:** Even with fixes 1 and 2, the user was still not logged in after returning from Microsoft.

**Root cause:** .NET 8 Blazor Web App renders in two phases:

1. **Static SSR** (HTTP request scope) — `App.razor` renders, middleware runs, `EntraTokenHolder` IS populated in this scope.
2. **Interactive Server circuit** (new DI scope) — `<Routes @rendermode="@InteractiveServer" />` gets a brand-new scope. A fresh empty `EntraTokenHolder` is injected. `MainLayout.OnAfterRenderAsync` runs here — the token is gone.

The token was written into scope #1 and read from scope #2 (always empty).

**Fix — `PersistentComponentState` bridge:**

| Component | Phase | Role |
|---|---|---|
| `EntraTokenPersister.razor` | SSR / App.razor | `RegisterOnPersisting` → serializes `SerializedEntraToken` JSON into the rendered HTML |
| `MainLayout.OnInitialized` | Circuit | `TryTakeFromJson("EntraToken")` → restores `EntraTokenHolder` in circuit scope before `TryBridgeEntraAuthAsync` runs |

**Files changed:**
- `Ben.Web.WebApp/Services/EntraTokenHolder.cs` — added `SerializedEntraToken` record
- `Ben.Web.WebApp/Components/EntraTokenPersister.razor` — new SSR component
- `Ben.Web.WebApp/Components/App.razor` — added `<EntraTokenPersister />` before `<Routes />`
- `Ben.Web.WebApp/Components/Layout/MainLayout.razor` — injected `PersistentComponentState`; added `TryTakeFromJson` in `OnInitialized`
