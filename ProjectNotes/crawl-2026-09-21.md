## Findings

### Code and logic

**C1 — The free account's storage cap does not see place evidence — or anything but field
sessions.** `AccountStorageGuard.UsedBytesAsync` sums only unpublished, investigation-less
field-session files; its own comment says *"when a second kind of personal upload appears, one
place decides what 'kept to yourself' means."* Item 250 P1 added that second kind today and did
not touch it: `PlaceEvidenceController.Add` stores under the person and neither checks nor counts
against the cap, so anyone signed in can upload without limit to a public place. On master,
migrated, **not yet deployed**. The wider question is older: equipment photos, audio clips, video
projects and feed media are all stored under the person and none of the ten controllers that do so
ask the guard. Whether the 2 GB should cover all personal uploads is a design decision for Ben; the
place-evidence omission is simply mine.

**C2 — A person who added place evidence cannot be deleted.** `AppUserPurge` does not know
`PlaceEvidence`; `AddedByAppUserId` is NoAction, so the census counts the rows and correctly
refuses. Needs a decision, not just code: are their contributions to a public archive deleted
with them (the free-lane rule for personal sessions) or anonymised to "a former contributor"?

**C3 — A guide who issued a guest code cannot be deleted while it exists.**
`InvestigationJoinCode.CreatedByAppUserId` is non-null and unswept. Consistent with every other
auditable row here, so lower priority — but codes expire in 24h and could simply be swept.

**C4 — The anonymous code look-up has no rate limit.** `PublicInvestigationCodeController.Look`
(`/tonight/{code}`) is `[AllowAnonymous]` with no `[EnableRateLimiting]`. The typed-code space is
30⁸ ≈ 6.5×10¹¹ and codes expire, so guessing is not a practical way in, but the handover door
beside it carries `AuthPolicy` and this should match. Same question for `PublicEventPassController`.

**C5 — Ingest re-encodes to JPEG but keeps the original file name.** A `corridor.png` served as
`image/jpeg` under the name `corridor.png`. A download gets a `.png` name with JPEG bytes. The
feed has done this since ingest was built; place evidence inherits it. Cosmetic until somebody
opens the download in a tool that trusts the extension.

**C6 — Merging two places DELETES the losing place's evidence and pictures.** `AdminPlaceMergeController`
repoints investigations, cases, calendar events, sessions and rooms onto the survivor, then deletes
the loser. It does not know `PlaceEvidence`, whose key to `Place` is `OnDelete(Cascade)` — so the
loser's contributions go with it, silently. Data loss, introduced today with item 250; the merge
screen exists precisely because duplicate places happen (item 88's dedup rule). **Top of the
morning's list.**

**C7 — A guest code can be issued on a visit to somebody's home, and the anonymous look-up hands
a stranger the unredacted title.** Neither `InvestigationJoinCodeController.Issue` nor
`GuestCodes.IssueAsync` asks the place's kind or the case's private-engagement flag, so a guide can
print a code for an investigation at a private residence. Then `/tonight/{code}` — anonymous by
design — returns `investigation.Title` raw. For a case-bound visit that title can carry the
client's name (the public place page runs the same field through `CaseProseRedactor.RedactFor`
precisely because of this, item 184), and a redeemed code then lets a stranger upload into that
case's evidence. `Redeem` and `Mine` return the same raw title. Introduced today with item 248; on
master, migrated, **not yet deployed**. The fix is two-part: refuse to issue on a
`PrivateResidence` place or a private-engagement case (in words), and redact the title on all
three anonymous/guest answers the way the place page does. **Ahead of C6 in the morning.**

**C8 — Anyone can now create a place, and nobody can delete one.** Item 250 opened `/places/new`
to every signed-in account; the only removal path is the SuperAdmin merge screen, which needs a
survivor to merge into. A junk or malicious place (a real person's home entered as a "public
location", say) has no removal path except merging it into something else. Needs a
delete-or-hide door with the same "in words" refusals the rest of the site has, and a way to
demote a place to private residence, which today only a hand-written statement can do.

## Visual pass

`VisualAuditWalk` (contrast, clipped content, text on a card edge — desktop width, 43 routes as
visitor / member / superadmin) passed both hard checks: **nothing clipped, no text on a card's
edge, anywhere.** `VisualShots` photographed the id-bearing screens at 375 and 1280 for reading.
Reports in the session scratchpad under `visual/`.

**V1 — The guest-code sheet prints the API's address when `SiteIdentity.BaseUrl` is unset.**
Photographed: *"Or type this at 127.0.0.1:5252/tonight"*, and the QR encodes the same. My `JoinUrl`
fallback takes `Request.Host`, which on the API is the API. Production sets `BaseUrl`, so the
live sheet is right — but UAT's appsettings may not, and a printed sheet with an unreachable
address is worse than no sheet. The join page beside it computes the same address a second way
(`NavManager.BaseUri` → "localhost/tonight"), so two screens disagree about one URL. Fix: one
source of truth — refuse to make a sheet, in words, when the site has no configured origin,
rather than fall back to something a phone cannot reach. Introduced today.

**V2 — A public place page at phone width opens with a wall of chips.** Seven action chips
("Rooms · Paranormal365", "Our venue", "Open a case here", "Investigate here", then the same for
BenCo) wrap over six lines before a reader on a phone sees a single fact about the place. Pre-
existing, but item 250 makes these pages worth visiting on a phone. One menu per group — or one
"Work here…" menu — at narrow widths.

**V3 — Theme contrast, judgement level — measured in LIGHT mode (see W7).** `text-warning` measures 2.62:1
(dashboard: "No Apple sign-in has been…"; org subscriptions: "→ Small group at renewal"),
`text-success` / `bg-success` 3.35:1 (the "+5" vote badges on the home page, "✓ Accepting new
cases" on /find), `btn-outline-secondary` 4.45:1. None fails hard; all are under AA for body
text. These are Bootstrap's own light-theme weaknesses (`text-warning` on white is famously under
AA); the dark theme was **not measured** and may be better or worse. Re-run the audit in dark
mode (W7) before choosing which variant to brighten.

**V4 — The dashboard chart legend is hard-coded dark grey.** `span.apexcharts-legend-text` at
`rgb(80,80,80)` — fine on the light theme the audit ran in, and near-invisible on dark if the
chart does not re-theme, which is what a hard-coded colour usually means. Unverified on dark;
cheap to check and cheap to fix (ApexCharts takes a legend colour option).

**V5 — A place's description has no heading.** On the visitor page it sits as a bare paragraph
between the map and the figures; a reader does not know it is *about the place* rather than a
caption. A small "About this place" heading. Introduced today.

**V6 — The handover reset page offers a way out that cannot work.** With `handover=1` the page
is deliberately identical to an ordinary reset, but its "Link expired? Request a new one" leads to
forgot-password — which refuses an unconfirmed address, and a handover reader's address is
unconfirmed by definition. If their link has expired they are sent somewhere that will tell them
"invalid" for a reason nobody explains. On `handover=1` that line should say what the endpoint
already says: ask whoever set the account up to send it again. Introduced today.

**W6 — The audit reports 1.00:1 where it means "could not measure".** `bgOf` assumes white when no
ancestor has an opaque `background-color`, so text over a gradient or an image (pricing band
headers, org-card initials) is measured against white and reported at 1.00:1. Those are not
faults; the audit should say "unmeasurable — gradient/image background" and move on, or a reader
in the morning will chase six ghosts before finding the real ones.

**V7 — The Investigations tab header collides at phone width.** Photographed at 375: the
"Investigations" heading, its help mark, and the "Schedule an investigation" button share one
row that does not wrap, and the intro paragraph ("Everywhere this group has worked…") is squeezed
into a ninety-pixel column beside the button. Pre-existing; the tab strip also runs off the right
edge ("Investi…"), which is tolerable but worth a scroll affordance. The new Guest-code button
sits in the grid's Actions column below the fold and was not verified at 375.

**W7 — The audit and the light-utility guard disagree about `alert-light`, and the audit is
wrong.** It reported `div.alert.alert-light` at 2.10:1 on `/notifications` and `/my-events`. The
guard's remarks say the theme redefines `--bs-light-bg-subtle`, `--bs-light-text-emphasis` and
`--bs-light-border-subtle` for dark mode, and `wwwroot/css/themes/night.min.css` confirms it
(#343a40 / #f8f9fa / #495057 — about 11:1). Neither theme produces 2.10:1 from those values, so
the measurement is off. **Settled: the audit has no dark-mode bootstrap** — no `ContextOptions`
override, no init script, and `BenTestBase` sets no colour scheme — so it ran in light mode, where
`alert-light` is #fcfcfd on #495057 (about 7:1) and still not 2.10:1. So the number is wrong in
either theme; `bgOf` is reading the wrong ancestor. Two fixes: give the audit the help captures'
dark-mode bootstrap (and run it in both), and make `bgOf` report which ancestor supplied the
background. Every contrast figure in V3 is a light-theme number until then. Also worth deciding
on purpose: what theme does a first-time visitor with no localStorage actually get?
